# dawn4k Acid Suite and Distribution Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Réutiliser le catalogue WebGPU publié pour qualifier le backend Dawn desktop, conserver sa provenance et préparer les deux publications.

**Architecture:** dawn4k-suite est un exécutable KMP non publié qui fournit les adapters/devices réels à AcidContext. La logique fonctionnelle de sélection/statuts est testée séparément ; CI et publication sont configurées sans suites de tests d'infrastructure. Les snapshots évoluent volontairement, leurs empreintes sont des preuves d'exécution, pas des locks.

**Tech Stack:** Kotlin 2.4.20, JDK 25, Gradle 9.6.1, dawn4k, suite-core/suite-acid-tests 0.1.0-SNAPSHOT, kotlinx.coroutines 1.11.0, kotlinx.serialization JSON 1.11.0, Python 3 pour watchdog/validation rapports.

**Spec:** `docs/superpowers/specs/2026-10-02-dawn4k-design.md`.

## Global Constraints

- Plans 01 et 02 achevés/revus avant de revendiquer la qualification du backend.
- Dépendances WebGPU `0.1.0-SNAPSHOT` évolutives ; aucune copie des interfaces, descriptors ou cas acides.
- Runner non publié ; publications `org.graphiks:dawn4k-native:0.1.0-SNAPSHOT` et `org.graphiks:dawn4k:0.1.0-SNAPSHOT`.
- JVM desktop macOS ARM64/Linux x64, K/N macosArm64/linuxX64 ; headless Metal/Vulkan, jamais Null comme preuve GPU.
- Timeout 30 secondes par cas ; watchdog de processus 1800 secondes pour un run complet.
- Référence examinée 123 cas / 118 obligatoires / 5 optionnels ; accepter le catalogue réellement résolu, pas une constante de nombre de cas qui empêcherait les évolutions.
- `unsupported` réservé aux requiredFeatures optionnelles absentes ; absence GPU = `not-run`, timeout/exception/assertion = `failed`.
- Toute publication distante, changement de ruleset GitHub ou merge demande une autorisation distincte.
- Aucun test d'infrastructure à créer : pas de tests des tâches Gradle, des scripts de provenance/rapports, des politiques CI ou de la publication. Conserver les tests fonctionnels du runner et le catalogue acide ; les commandes usuelles vérifient configuration et publication locale.

## Review Focus

1. Sélection vide/inconnue/dupliquée ou rapport partiel : non-zero, jamais un rapport vert incomplet, tâche 1.
2. Pas d'adapter ou feature obligatoire manquante : not-run/failure, pas unsupported pour masquer le défaut, tâche 2.
3. Callback d'erreur livrée après assertions : drain et contrôle avant passed, tâche 2.
4. Cache SNAPSHOT périmé ou publications partiellement rafraîchies : provenance/hashes et compilation contract, tâche 3.
5. Coordonnées/transitives de publication : revue des POM/module et exemple d'usage documenté, tâche 5.

```kotlin
fun selectCaseIds(known: Set<String>, requested: Set<String>?): Set<String> {
    require(known.isNotEmpty()) { "Empty resolved catalogue" }
    if (requested == null) return known
    require(requested.isNotEmpty()) { "Explicit selection cannot be empty" }
    require((requested - known).isEmpty()) { "Unknown case ids: ${requested - known}" }
    return requested
}

fun exitCode(results: List<CaseResult>, expectedIds: Set<String>): Int {
    if (expectedIds.isEmpty()) return 1
    if (results.size != expectedIds.size || results.map { it.id }.toSet() != expectedIds) return 1
    return if (results.all {
        it.status == CaseStatus.Passed ||
            (!it.mandatory && it.status == CaseStatus.Unsupported &&
                !it.diagnostic.isNullOrBlank() && it.missingFeatures.isNotEmpty())
    }) 0 else 1
}
```

coroutines. Aucun plugin publish. Les tests de sélection utilisent les ids
unitaires ci-dessus ; un test catalogue réel doit comparer ses ids uniques et
les `contract` non vides, sans exiger un nombre hardcodé éternel.

```text

sinon request device(requiredFeatures, onUncapturedError collectée)
```

`CaseResult.mandatory = case.requiredFeatures.isEmpty()`. Une assertion/exception
de cas est failed ; absence d'adapter est not-run ; aucune downgrade d'une
méthode manquante en unsupported. Les cas de contexte possèdent leurs objets

device partagé en guise de fresh adapter.

première donne failed, la seconde est propagée après cleanup. Les erreurs
collectées doivent être thread-safe ou dispatchées sur le worker owner ; pas
de mutableList lue/écrite sans discipline si les upcalls sont spontanées.

Implémenter le drain sur le worker/pump réel ; documenter son contrat et ajouter
un test où une erreur n'arrive qu'après le dernier submit.

Le processus écrit un rapport intermédiaire atomique après chaque cas puis un
rapport final. `scripts/run-dawn-suite.py` lance la commande JVM/K/N avec

report absent/invalide ou exit !=0 => échec, jamais acceptation du dernier état
partiel. Ceci borne également un C call bloqué que la coroutine ne peut annuler.

```kotlin
fun sha256(file: File): String {
    val digest = MessageDigest.getInstance("SHA-256")
    file.inputStream().use { input ->
        val bytes = ByteArray(8192)
        while (true) {
            val count = input.read(bytes)
            if (count < 0) break
            digest.update(bytes, 0, count)
        }
    }
    return digest.digest().joinToString("") { "%02x".format(it.toInt() and 0xff) }
}
```
