# dawn4k Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Livrer un backend Dawn desktop implémentant Graphiks WebGPU, composé de deux bibliothèques dans un monorepo et validé par la suite acide partagée.

**Architecture:** kextract génère la surface C dans dawn4k-native, avec kffi au runtime. dawn4k adapte les handles/descriptors/callbacks au contrat public WebGPU. Un runner headless indépendant consomme les tests existants, sans les copier.

**Tech Stack:** Kotlin 2.4.20, JDK 25, Gradle 9.6.1, Kotlin Multiplatform, kextract, kffi, Dawn chromium/8077, kotlinx.coroutines et Graphiks WebGPU 0.1.0-SNAPSHOT.

**Spec:** `docs/superpowers/specs/2026-10-02-dawn4k-design.md`.

## Global Constraints

- Lire la spécification et le plan concerné avant toute tâche ; documents proposés pour revue, aucune implémentation commencée.
- WebGPU reste `0.1.0-SNAPSHOT` évolutive, sans pins horodatés ni verrouillage empêchant sa republication.
- Desktop initial : JVM macOS ARM64/Linux x64 et K/N macosArm64/linuxX64.
- Dawn release `v8077.0.0`, révision `531028367c60ce07251ec0231c1b95bedb4495bc` ; header `dawn/webgpu.h`.
- Deux publications `org.graphiks:dawn4k-native` et `org.graphiks:dawn4k` ; runners non publiés.
- Les commandes ci-dessous décrivent la future vérification ; elles n'ont pas été exécutées pour ce travail documentaire.
- Ne pas publier à distance, merger, supprimer du travail utilisateur ou déléguer sans méthode d'exécution choisie.
- Tests d'infrastructure exclus à la demande de l'utilisateur : build/configuration Gradle, téléchargement/extraction, génération, packaging/publication, provenance et politiques CI. Conserver les protections d'exécution et commandes usuelles, ainsi que les tests ABI, fonctionnels WebGPU/callbacks et du runner acide.

## Review Focus

1. ABI des CallbackInfo par valeur et `WGPUStringView` : comparaison C/Kotlin et callback réelle, plan 01 tâches 3–4.
2. Callback inline/différée après annulation ou fermeture : résultat possédé libéré une fois, plan 02 tâches 1–2.
3. Defaults, nulls et bornes ULong : pas de troncature ni enum par ordinal, plan 02 tâches 3–4.
4. Destruction, mémoire mappée et erreur scope : writes réels, pas de UAF ni faux succès, plan 02 tâches 4–5.
5. Snapshot évolutive, feature absente et runner sans GPU : provenance honnête et statut distinct, plan 03 tâches 1–3.

Ce document est l'index ; les étapes d'implémentation et fichiers précis sont dans les trois
plans exécutables suivants. Les plans ne sont pas parallélisables en entier :
leurs interfaces sont produites dans l'ordre.
Les tâches fonctionnelles gardent leurs tests ; les tâches d'infrastructure
se limitent à configuration, commandes de build et revue des outputs, sans

## Jalons d'acceptation

- [ ] **N — bas niveau** : les quatre configurations chargent/lient Dawn et exécutent une callback réelle ; le test ABI ne signale aucun écart.
- [ ] **B — backend** : un buffer écrit/mappé, un dispatch compute et un rendu offscreen ont un oracle de données CPU, pas seulement une absence d'exception.
- [ ] **S — suite** : le catalogue résolu est complet, tous les cas obligatoires sont `passed`, seuls les manques de features optionnelles sont `unsupported`.
- [ ] **D — distribution** : les deux publications Maven locales sont produites, leurs variantes/transitives relues et leur consommation documentée ; aucun harness de test packaging/publication.
- [ ] **Documentation** : versions résolues, configurations exécutées et limites connues sont publiées sans revendication de conformité complète ni de performance.

## Revue et exécution

Avant exécution, faire relire ensemble la spécification et les trois plans.
Les snippets définissent des contrats locaux ou montrent des tests ; les corps
FFI dépendent de la sortie kextract réellement obtenue et ne sont pas présentés
comme du code déjà compilé. Les écarts découverts dans une snapshot WebGPU plus
récente demandent une mise à jour coordonnée de la matrice/du plan, pas un faux
adapter conservant silencieusement l'ancien contrat.

Méthodes à choisir : subagents avec revue par tâche, ou exécution native dans
cette session avec revue de branche finale. Recommandation : revue par tâche
pour les premières frontières ABI/callbacks, vu le coût d'un défaut mémoire.
