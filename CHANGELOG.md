## [Unreleased]

### Fixed
- `Dawn4kToolkitInstance.close()` now marshals its teardown onto the execution owner instead of assuming the caller already did: a close from any other thread could race the event-loop pump's `processEvents()` iteration and fail with `cannot close during processEvents()` (seen on loaded CI runners). A second `close()` is now a no-op rather than racing the first.

### Changed
- dawn4k itself joins the `org.graphiks.webgpu` Maven group: the published coordinates are now `org.graphiks.webgpu:dawn4k`, `:dawn4k-native` and `:dawn4k-webgpu-toolkit`. Artifact ids keep their `dawn4k-` prefix (unlike WebGPU's own stripped names) so the Dawn-backed modules stay identifiable inside the WebGPU family; consumer dependency strings must add the `webgpu` segment.
- CI: the Apple toolkit GPU suites share one macOS runner with the device-compile and publication checks staggered behind it, staying within the runner pool's variable capacity; Android qualification no longer waits for them, native-heavy macOS jobs cache `~/.konan`, and superseded pull-request runs are cancelled.
- WebGPU dependencies moved to the current `org.graphiks.webgpu` Maven group (`api`, `descriptors`, `toolkit-*`, `suite-*`), matching WebGPU #152; the legacy `org.graphiks` group coordinates are gone, which also removes the duplicate webgpu-api klib/AAR on native and Android classpaths.
- kffi `1.0.0-SNAPSHOT` → `0.1.0`, the first Maven Central release: the artifacts now live under the `org.graphiks.kffi` group (`kffi`, `objc-jvm`, `win32-jvm`, `x11-jvm`), so the kffi filters are dropped from the snapshot repository.
- Dawn prebuilt archives re-pinned `v8077.0.0` → `v8077.0.1` (same `chromium/8077` revision `5310283…`): the patched Metal backend only calls `setDepthClipMode` when a pipeline requires clamping, so Metal API Validation no longer aborts iOS/tvOS simulator launches (dawn-packer patch mirroring upstream google/dawn#66; verified by launching the sample app with the validation layer forced).
- Published acid-suite dependencies and execution moved out of the binding into a dedicated desktop validation module; binding-specific tests remain in `:dawn4k`.
- The Linux demo uses published `kffi-x11` bindings and generated X11 event/window layouts instead of handwritten Xlib downcalls and ABI offsets.
- Kotlin 2.4.0 → 2.4.10
- Gradle 9.5.0 → 9.6.1 → 9.8.0
- Added blocking pull request policy checks aligned with `CONTRIBUTING.md`.
- The template `shared` module is replaced by `:dawn4k-native`.
- Renamed the generated bindings package from `org.graphiks.dawn4k.raw` to `org.graphiks.dawn4k.native`.

### Added
- Optional `dawn4k-webgpu-toolkit` module (`org.graphiks.webgpu:dawn4k-webgpu-toolkit`): Dawn (WebGPU) extension providing managed GPU sessions, native surface presentation and desktop GLFW window hosting for the Graphiks toolkit, with contract coverage from the toolkit TCK.
- Strict toolkit publication/coverage checks and platform CI for JVM macOS/Windows/Linux x64/ARM64, Native macOS/Linux X11 and Wayland, Android Vulkan, and ARM64/Intel Apple simulators. Physical iOS/tvOS device compilation is reported separately from GPU execution.
- Unpublished `:dawn4k-acid-tests` module running the complete Graphiks foundation registry on JVM, macOS ARM64 and Linux x64, with isolated GPU cases, per-case JSON reports and CI integration. Usage and result interpretation are documented in `docs/docs/acid-tests-verification.md` and its French translation.
- Android Vulkan and iOS Metal demo applications sharing the adaptive Compose UI, native surface ownership, lifecycle controls and mobile tests.
- Compose controls above the Metal particle demo: pause/resume, reset and GPU-limited particle counts, with a draggable title strip and close button for the transparent undecorated window.
- `:dawn4k-demo`: macOS desktop demo (Compose Desktop) rendering the `suite-demos` `ParticleScene` through the `:dawn4k` backend — a real window over a Dawn Metal surface, with the surface living inside the demo module and `:dawn4k` exposing only minimal platform-integrator accessors (`DawnContext.nativeBridge()`, `DawnDevice.nativeHandle()`, `DawnAdapter.nativeHandle()`).
- `dawn4k-native`: Dawn (WebGPU) desktop, Android, iOS and tvOS bindings generated by kextract (JVM, Android arm64-v8a/x86_64, iOS/tvOS arm64/simulator, macOS ARM64, Linux x64).
- `:dawn4k`: WebGPU backend implementing the published Graphiks contract over generated Dawn bindings, with caller-owned threading, explicit `DawnContext.processEvents()` progression, `hasPendingOperations()`, and resource-owning wrappers with registry-backed teardown. The contract includes typed usage masks, partial required limits, stable nullable descriptor slots and shared cancellable `GPUDevice.awaitLost()` observation. Context closure requires settled operations and closed children; device teardown is explicitly progressed. Shared-device concurrency opts into `DawnConfig.implicitDeviceSynchronization` (default `false`), requesting Dawn's native synchronization feature. Independent-encoder/readback and OS-thread-local error-scope witnesses execute on JVM and Kotlin/Native; no speedup is claimed. Covers the full `:dawn4k-native` Kotlin target matrix: JVM/macOS ARM64 Metal and Android Vulkan tested; Linux x64, iOS and tvOS compiled, with runtime validation requiring appropriate hosts/devices. Borrowed mapped ranges use the upstream `ArrayBuffer.wrap(address, size)` of `webgpu-api` (Graphiks-org/WebGPU#135); JVM/Android share monitor actuals.
- KMP project template (Android, iOS, Desktop)
- Clean Architecture / DDD
- Maven Central publishing via Vanniktech
- Multilingual docs (EN/FR) MkDocs + Dokka
- GitHub templates (issues, PR)
- Code of Conduct, CONTRIBUTING, SECURITY, SUPPORT, CHANGELOG

### Removed
- Legacy `dawn4k-toolkit-core`, `dawn4k-toolkit-surface` and `dawn4k-toolkit-glfw` modules, folded into `dawn4k-webgpu-toolkit`.
- Template `shared` module (sample Android/iOS/desktop layers).
- `:native-smoke` module; functional validation is delegated to the shared acid test suite.
- Standalone Maven coordinate consumer verification: `scripts/verify-toolkit-consumers.py`, `scripts/run-toolkit-consumer-artifacts.py`, the `toolkit-published-consumers` CI artifact and the `published-linux` job. Publication keeps `verifyToolkitPublication` and the platform GPU coverage.

### Changed
- Replaced the Dokka GFM and Python post-processing pipeline with Dokka for Material for MkDocs.

### Fixed
- Windows CI no longer rejects the Linux Dawn carrier bundle: the generator identity is now computed over line-ending-normalized script bytes (a Windows `autocrlf` checkout hashed differently than the Linux-built bundle), and `.gitattributes` pins `*.py`/`*.sh`/`gradlew` to LF so every host checks out identical bytes.
- Gradle and IDE imports no longer fail on hosts that cannot produce the Linux Dawn carrier and GLFW archives: the `linuxX64` target is now declared only on Linux x86_64 hosts or when both verified `dawn.nativeBundle.linuxX64` and `glfw.nativeBundle.linuxX64` bundles are supplied, mirroring the CI flow and `wayland.targets`. Unchanged elsewhere: Linux hosts and bundle-provided builds keep the full target.
- Native publication embeds Dawn and GLFW archives with relocatable linker metadata; Linux packages the verified Dawn shared runtime through a typed, thread-safe carrier instead of checkout-specific runtime paths. JVM resources include the Windows Dawn runtime, and Android surface JNI ships consumer keep rules for minified apps.
- Buffer mapped views use absolute offsets, default to the remaining buffer size and reject overlapping views synchronously; timestamp query sets require the feature to be enabled on the device without producing a validation-scope error.
- Blank Compose/Metal demo window, fixed-size surface rendering and animation stalls during mouse dragging; native UI work now runs on AppKit in common run-loop modes with explicit resource cleanup.
- Default snapshot publication version when no workflow version is provided.
- Maven Central publication: `:dawn4k` and `:dawn4k-native` now apply the publication convention with `org.graphiks` coordinates and Graphiks POM metadata, the workflow publishes from a macOS runner so Apple variants are built (they cannot be cross-compiled on Linux), and the Gradle task selector matches the publishing subprojects instead of the root project.
